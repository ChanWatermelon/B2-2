# 일일 AI 뉴스 자동 요약 시스템

RSS로 기술 뉴스를 수집해 Gemini로 3줄 요약한 뒤 Notion 데이터베이스에 자동 적재하는 무인 워크플로우입니다.
매일 08:00(KST)에 사람 개입 없이 실행됩니다.

```
[매일 08:00 트리거] → [RSS 수집] → [AI 주제 필터] → [중복 체크] → [Gemini 요약+감성분석] → [Notion 저장]
                                                                        ↳ 실패 시 재시도 2회 → 이메일 알림
```

## 스택

| 역할 | 도구 | 비고 |
|---|---|---|
| 자동화 엔진 | Make (구 Integromat) | 모듈 8개 + 필터 2개 |
| 데이터 소스 | 전자신문 IT RSS (`https://rss.etnews.com/03.xml`) | 2026-08-10 동작 확인 |
| 생성형 AI | Google Gemini API (`gemini-2.5-flash`) | thinking 비활성 · 구조화 출력 |
| 저장소 | Notion Database | 액세스 토큰(Internal) 연동, Data Source API |

**구축 상태** — 2026-08-10 end-to-end 동작 확인 완료. RSS 수집 → 필터 → 중복 체크 → Gemini 요약·감성분석 → Notion 저장까지 전 구간이 사람 개입 없이 실행됩니다. 실전 전환에 남은 작업은 §6-2를 참고하세요.

## 2. 주제 필터링 기준

### 2-1. 필터 조건

기사는 **두 조건을 모두 통과해야** 다음 단계로 넘어갑니다.

**조건 A — 키워드 매칭** (제목 + 본문 대상)

검사 대상을 `lower()`로 소문자화한 뒤, 소문자 정규식으로 부분 검색합니다.

```
왼쪽:   {{lower(2.title)}} {{lower(2.description)}}
연산자: Text operators → Matches pattern
```

```regex
(ai|a\.i\.|인공지능|생성형|머신러닝|딥러닝|llm|sllm|거대언어모델|파운데이션 모델|초거대|
챗봇|chatgpt|gpt|gemini|제미나이|claude|클로드|openai|오픈ai|앤스로픽|
엔비디아|nvidia|gpu|npu|hbm|온디바이스|ai 반도체|추론 모델|에이전트)
```

> **`(?i)` 인라인 플래그를 쓰지 않은 이유** — Make의 정규식은 JavaScript 엔진을 사용하는데, JavaScript는 `(?i)` 형태의 인라인 플래그를 지원하지 않습니다. 넣으면 잘못된 그룹으로 처리되어 필터가 조용히 아무것도 통과시키지 않습니다. 대신 검사 대상과 패턴 **양쪽을 소문자로 맞추는** 방식으로 같은 효과를 냈습니다. 한글 키워드는 대소문자 개념이 없어 영향을 받지 않습니다.

**조건 B — 신선도**: 발행일시가 `현재 시각 − 36시간` 이후

### 2-1-b. 패턴 변형 (범위 조정용)

운영 중 통과 건수를 보고 아래 세 패턴 사이에서 고를 수 있습니다. **채택한 것에 맞춰 §2-2의 근거도 함께 고쳐야 합니다.**

P3에서 `출시`, `플랫폼`, `투자`, `기술` 같은 단어는 **일부러 제외**했습니다. IT와 무관한 기사까지 전부 걸려 필터가 없는 것과 같아지기 때문입니다. 필터를 넓힌다는 것은 "아무거나 통과시킨다"가 아니라 "주제 경계를 다시 긋는다"는 뜻입니다.

> ⚠️ **P3 채택 시 모듈 1의 `Maximum number of returned items`를 `3`으로 낮추세요.** IT 피드 기사의 절반 이상이 통과하므로 20으로 두면 하루 Gemini 호출 10회 이상, Notion 저장 10건 이상이 되어 무료 티어를 빠르게 소진합니다.

### 2-2. 키워드 목록과 선택 이유

| 그룹 | 키워드 | 선택 이유 |
|---|---|---|
| 상위 개념 | AI, 인공지능, 생성형, 머신러닝, 딥러닝 | 주제의 정의 그 자체. 이것만으로는 기사를 놓치기 때문에 아래 그룹을 추가 |
| 기술 용어 | LLM, sLLM, 거대언어모델, 파운데이션 모델, 초거대, 추론 모델, 에이전트 | 한국 언론은 제목에 "AI"를 안 쓰고 "LLM 공개"처럼 쓰는 경우가 많음 |
| 제품·기업 고유명사 | ChatGPT, Gemini, Claude, OpenAI, 앤스로픽, 엔비디아 | **재현율(recall)을 가장 크게 올려주는 그룹**. 제품명만 등장하고 "AI"라는 단어가 아예 없는 기사가 실제로 존재 |
| 하드웨어 인접 | GPU, NPU, HBM, AI 반도체, 온디바이스 | AI 산업 기사의 상당수가 반도체 관점에서 작성됨 |

**설계 원칙 3가지**

1. **재현율 우선, 정밀도는 AI에 위임.** 필터는 넓게 잡고, 실제로 AI 기사인지 판단하는 정밀한 작업은 Gemini의 요약 단계에서 자연스럽게 걸러지도록 했습니다. 필터를 좁게 잡으면 "수집 0건"이 자주 발생해 시스템이 매일 실행된다는 요구사항을 만족하지 못합니다.
2. **한글·영문 표기를 쌍으로 등록.** `NVIDIA`/`엔비디아`, `OpenAI`/`오픈AI`처럼 국내 기사는 표기가 섞여 있어 한쪽만 넣으면 절반을 놓칩니다.
3. **`GPT`는 단독 등록하되 `AI`는 단어 경계를 두지 않음.** `AI`는 `MAIL` 같은 단어에도 포함될 수 있지만, 한글 기사에서 오탐 비용(잘못된 기사 1건 요약)이 미탐 비용(그날 수집 0건)보다 훨씬 작다고 판단했습니다.

### 2-3. 왜 36시간인가

시나리오는 매일 08:00에 한 번 돕니다. 창을 정확히 24시간으로 잡으면, 전날 07:50에 발행된 기사는 전날 실행에도 안 잡히고(아직 발행 전) 오늘 실행에도 안 잡히는(24시간 초과) **경계 사각지대**가 생깁니다. 36시간으로 12시간의 여유를 두어 이 구멍을 막았고, 중복 저장은 링크 해시가 별도로 막아주므로 창을 넓혀도 부작용이 없습니다.

### 2-4. 데이터 소스 선택 이유

`https://rss.etnews.com/03.xml` (전자신문 IT 섹션)을 선택했습니다.

- **`description` 필드가 300~420자로 충분히 김.** 원문 페이지를 크롤링하지 않고도 3줄 요약이 가능해, 크롤링 실패(403·페이월·JS 렌더링)라는 장애 요인을 아예 제거할 수 있습니다.
- **`guid`, `pubDate`, `link`가 모두 표준 RSS 2.0 형식**으로 제공되어 중복 키와 발행일시 매핑이 깔끔합니다.
- **IT 섹션이되 AI 전용은 아님.** 전자신문은 AI 전용 피드(`04046.xml`)도 제공하지만, 그것을 쓰면 "수집 후 주제 필터링"이라는 과제의 학습 목표가 사라집니다. 일부러 한 단계 넓은 IT 피드를 받아 워크플로우 안에서 필터링합니다.

**검토했으나 채택하지 않은 후보**

| 후보 | 제외 이유 |
|---|---|
| Google News RSS 검색 | `link`가 `news.google.com/rss/articles/...` 리다이렉트 URL이라 중복 키가 불안정하고, `description`이 제목 반복 수준이라 요약 재료가 부족 |
| ZDNet Korea (`zdnet.co.kr/news/news_xml.asp`) | 2026-08-10 확인 시 HTTP 404 |
| 블로터 (`bloter.net/rss/`) | HTTP 403 (봇 차단) |
| TechCrunch (`techcrunch.com/feed/`) | 정상 동작하나 영문. **예비 피드로 등록**해 두었습니다 (아래 참고) |

## 3. 에러 처리 정책

### 3-1. 정책 요약

| # | 상황 | 처리 | 재시도 | 근거 |
|---|---|---|---|---|
| E1 | RSS 서버 응답 없음 / 파싱 실패 | 시나리오 중단 + 이메일 알림 | **2회** (5분 간격) | 일시적 네트워크 장애가 대부분. 2회 안에 회복되지 않으면 소스 자체 문제이므로 사람이 봐야 함 |
| E2 | 수집 기사 0건 (필터 통과 0건 포함) | **정상 종료** (에러 아님) | 없음 | 뉴스가 없는 날은 장애가 아닌 정상 상태. 여기서 에러를 내면 알림 피로가 쌓여 진짜 장애를 놓치게 됨 |
| E3 | Notion 중복 조회 실패 | Break → 재시도 | **2회** | 조회 실패 상태에서 저장을 강행하면 중복이 생김. 판단 불가 시 저장하지 않는 쪽이 안전 |
| E4 | Gemini API 실패 (429 / 500 / 타임아웃) | Break → 재시도 | **2회** (5분 간격) | 429는 대기하면 풀리는 종류. 단 무한 재시도는 비용 폭증 위험이 있어 2회로 상한 |
| E5 | Gemini 응답이 스키마와 불일치 | 해당 기사 건너뜀 + 로그 | 없음 | 같은 입력을 다시 넣어도 같은 결과가 나올 가능성이 높음. **재시도가 무의미한 오류는 재시도하지 않는다** |
| E6 | Notion 저장 실패 | Break → 재시도 | **2회** (5분 간격) | 마지막 단계라 여기서 유실되면 요약 비용이 통째로 낭비됨 |
| E7 | 연속 3회 실행 실패 | 시나리오 자동 비활성화 + 알림 | — | Make 기본 안전장치. 고장 난 시나리오가 조용히 operations를 태우는 것을 방지 |

### 3-2. 왜 이 정책인가

**① 재시도 상한을 2회로 고정한 이유**

재시도는 "일시적 장애"에만 효과가 있습니다. 3회 이상 실패한다는 것은 대개 영구적 문제(잘못된 API 키, 스키마 변경, 할당량 소진)이고, 이때 재시도를 계속하면 문제는 안 풀리면서 API 비용과 Make operations만 소모합니다. 2회 × 5분 간격이면 대부분의 일시적 장애(레이트 리밋, 순간 네트워크 끊김)를 흡수하면서 상한은 명확합니다.

**② `Break`를 쓰고 `Ignore`를 쓰지 않은 이유**

Make의 `Ignore`는 실패한 기사를 그냥 버립니다. 그런데 RSS `Watch` 트리거는 이미 읽은 항목을 다시 주지 않으므로, 버려진 기사는 **영원히 유실**됩니다. `Break`는 실패 지점을 "미완료 실행(Incomplete Execution)"으로 저장해 두었다가 재시도하기 때문에 유실이 없습니다. 그래서 시나리오 설정에서 `Allow storing of Incomplete Executions`를 켜는 것이 이 정책의 전제 조건입니다.

**③ E2(0건)를 에러로 처리하지 않은 이유**

"뉴스가 수집되지 않은 경우"는 요구사항에 명시된 처리 대상이지만, 처리 방식이 곧 알림은 아닙니다. 주말·연휴에는 IT 기사 자체가 적어 필터 통과 0건이 자연스럽게 발생합니다. 이를 에러로 잡으면 한 달에 몇 번씩 오탐 알림이 오고, 그러면 팀은 알림을 무시하게 되며, 정작 E4·E6 같은 진짜 장애를 놓칩니다. **알림의 가치는 희소성에서 나온다**는 판단으로 0건은 정상 종료 처리하고, 대신 Notion DB에 하루도 행이 늘지 않는 것으로 육안 확인이 가능하도록 했습니다.

**④ E5를 재시도하지 않은 이유**

에러를 "재시도하면 풀리는 것"과 "재시도해도 그대로인 것"으로 나누어 정책을 달리 적용했습니다. 429·타임아웃은 전자, 스키마 불일치는 후자입니다. 후자에 재시도를 걸면 실패 비용이 3배가 되면서 성공 확률은 그대로입니다.
